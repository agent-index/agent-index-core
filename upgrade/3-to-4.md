# Upgrade: agent-index-core v3.x → v4.0.0

**MAJOR-version migration (required reading before publishing).** The admin half must be done before core 4.0.0 is published to the org. The member half runs by itself during `@ai:update`.

## What changed

Core 4.0.0 removes the permission-change-helper. Every permission change now goes through the core procedure `/agent-index-core/internal/permission-changes.md`: list the changes, get a fresh confirmation, apply under the person's own credentials, verify on the backend, record. That procedure shipped in 3.32.0 and is unchanged.

Removed in 4.0.0:

- The `permission-change-helper` skill and the `pin-binary-version` task.
- The native binary `agent-index-show-plan`, its `agent-index://` URL handler and its browser review page.
- `build-permission-spec` (`lib/permission-spec/`) and the helper source (`lib/permission-helper-go/`).
- The org-config `binaries{}` block, the infrastructure-directory `binaries[]` array and the backend folder `/shared/dist/binaries/`.

A collection version that still calls the helper stops working on core 4.0.0: its permission steps have nothing to call. That is why the gate below exists.

## What does NOT change

- The permission-changes procedure, its trust rules and its approval record (`members/{member_hash}/state/permission-changes.jsonl`).
- `aifs_get_permissions` (read-only, any task may call it).
- Distribution through `/shared/dist/`, the manifest and its SHA gate. The manifest just has no binary entries.
- Member workspaces, credentials and installed capabilities.

## Admin half (before publishing core 4.0.0)

### 1. Gate: every installed collection must already use the procedure

**`@ai:publish-updates` enforces this gate itself (Step 0g, core 4.0.1 — findings 61, 64)** and halts before uploading anything when a row fails; this section defines the table it reads. Run it by hand only if you want to check before refreshing the clones.

Read org-config `installed_collections[]` (gdrive by id anchor, OneDrive by path) and check **every entry whose `status` is `installed` or `downloaded`** (`gatedownloaded`, finding 26: a downloaded collection is one `@ai:install-collection` away from running) — against the first release that moved it to the permission-changes procedure. **Compare the version the org will be on after the publish, not org-config's current value** (finding 61): the marketplace version is the refreshed marketplace clone's (org-config still says the old one until the publish writes it back), and a collection already upgraded with `@ai:upgrade-collection` counts at its uploaded `collection.json` version.

| Collection | Minimum version |
|---|---|
| `agent-index-marketplace` | 2.22.0 |
| `projects` | 4.4.0 |
| `strategy` | 1.3.0 |
| `library` | 1.7.0 |
| `brand-book` | 1.2.0 |
| `cx-studio` | 5.1.0 (released 2026-10-17; cx-studio 5.0.0 still calls the helper) |
| `client-intelligence` | 2.4.0 |
| `bug-reports` | 1.3.3 |

For any installed collection that is not in this table and is not first-party (third-party or org-authored), check its definitions for helper calls: search its `api/` folder (in the admin's local clone, or via `aifs_search` on the collection's id-anchored base) for `permission-change-helper` and `agent-index://`. A hit in a changelog is history and is fine; a hit in an `api/` task or skill is a live call.

**If any collection is below its minimum, or has a live helper call: stop.** Do not publish core 4.0.0. Tell the admin which collections to upgrade first, for example:

> "Core 4.0.0 can't be published yet. These collections still use the removed permission helper: `projects` 4.3.1 (needs 4.4.0), `acme-onboarding` (calls `permission-change-helper` in `api/grant-access.md`). Upgrade them first with `@ai:upgrade-collection`, then publish core again."

Only when every collection passes, continue.

The same table guards later installs: on core 4.0.0 or later, `install-collection` (marketplace 2.22.1+) refuses a collection below its minimum, or with a live helper call, and says which version to download instead.

### 2. Publish

Refresh the clones to core 4.0.0 (clone-script refresh), then run `@ai:publish-updates`. Its Step 0g re-checks the gate above. Publish-updates removes `/shared/dist/binaries/` from the backend: it lists the files, asks once, and deletes them. If the admin declines, the folder is left in place unused and the next publish offers it again.

### 3. Clear org-config `binaries`

The `binaries{}` block in org-config is no longer read by anything. Publish removes it during the same run (revision-aware write). If org-config still has `binaries` after the publish, remove that key: read org-config by id anchor, `aifs_stat` it for the revision, delete the key and write it back with `if_revision`.

### 4. Set the 3.x end-of-life date

Set `eol_date` on core 3.x: **3.x is supported until 2027-01-31.** Members still on a 3.x install see the session-start deprecation notice as that date approaches.

## Member half (during `@ai:update`)

`apply-updates` Step 1.6 removes whatever an older install left behind:

1. It deletes the old Node helper folder (`mcp-servers/permission-helper/`) if present.
2. It asks the member to run one command on their own machine, because the URL handler and binary live outside the Cowork sandbox (`<install_root>\agent-index-core\lib\uninstall` below is where an admin's clone has the script; on a member install apply-updates first copies it to `<install_root>/.agent-index/tmp/uninstall/` and uses that folder):
   - Windows: `powershell -ExecutionPolicy Bypass -File "<install_root>\agent-index-core\lib\uninstall\remove-permission-helper.ps1" -InstallRoot "<install_root>"`
   - macOS / Linux: `bash "<install_root>/agent-index-core/lib/uninstall/remove-permission-helper.sh" "<install_root>"`
3. The command prints one JSON line (`handler_removed`, `binary_removed`, `stray_ext_removed`, `errors`). The member pastes it back.
4. On success the member sees "✓ Removed the retired permission helper." and the step does not run again.
5. If removal fails, the update still completes. The member sees that the old helper is unused and safe to leave, and the next `@ai:update` offers the command again.
6. Separately from the command, it removes the retired `permission-change-helper` skill from the member's `member-index.json` and archives its installed folders to `members/{member_hash}/archive/{timestamp}-permission-change-helper/` (archived, not deleted; finding 69). This is part of the helper removal, so it needs no extra confirmation; the update plan says it happens. Without it the orphaned entry kept the core manifest sync stuck at 3.x (ms_prod_10). Any other core or marketplace capability that 4.0.0 dropped (e.g. `pin-binary-version`) is offered for the same archive in the update plan (apply-updates Step 3, "Retired capabilities").

A member who never had the helper sees the command once (the agent can't check the Windows registry); the script reports nothing to remove and exits cleanly.

Nothing else changes for members. Permission changes already used the in-chat confirmation table on 3.32.0 and later collection versions.

## Verification (admin, after both halves)

- org-config `agent_index_version` is 4.0.0 and has no `binaries` key.
- `aifs_exists("/shared/dist/binaries/")` is false.
- `/shared/dist/manifest.json` has no binary entries.
- One permission-changing task (for example `@ai:invite-member` on a test address) shows the confirmation table and verifies its changes.
